# Технічне завдання на розробку системи управління завданнями

## 1. Загальні відомості

**Назва програмного продукту:** Task Management API.

**Тип програмного продукту:** REST API та вебдокументація для взаємодії із системою управління завданнями.

**Предметна область:** управління проєктами та завданнями.

**Мова документації:** українська.

**Формат специфікації API:** OpenAPI YAML.

**Засоби розробки та документування:** OpenAPI, TypeScript, `openapi-typescript`, Zudoku, Node.js, npm, Git і GitHub Pages.

**Підстава для розробки:** навчальне завдання з дисципліни, що передбачає підготовку технічної документації до програмного продукту та її публікацію в мережі Інтернет.

### 1.1. Призначення документа

Це технічне завдання визначає мету, призначення, функціональні й нефункціональні вимоги, вимоги до інтерфейсів, тестування та документації програмного продукту Task Management API.

Документ використовується як основа для подальшого проєктування, розробки, тестування та супроводження системи.

### 1.2. Терміни та скорочення

- **API (Application Programming Interface)** — програмний інтерфейс для взаємодії між програмними компонентами.
- **REST** — архітектурний стиль побудови вебсервісів.
- **HTTP** — протокол передавання даних у вебсередовищі.
- **CRUD** — операції створення, читання, оновлення та видалення даних.
- **OpenAPI** — специфікація для формального опису HTTP API.
- **SDK (Software Development Kit)** — набір засобів для взаємодії з програмним продуктом.
- **Zudoku** — інструмент для створення вебдокументації API на основі OpenAPI.
- **Git** — система контролю версій.
- **GitHub Pages** — сервіс публікації статичних вебсайтів.

## 2. Призначення та цілі розробки

### 2.1. Призначення системи

Task Management API призначений для стандартизованого опису та організації взаємодії з даними про проєкти й завдання. Система має забезпечувати можливість отримання, створення, зміни та видалення відповідних ресурсів через REST API.

Специфікація OpenAPI описує структуру доступних операцій, параметри запитів, формати даних і відповіді сервера. Вебдокументація Zudoku надає розробникам зручний спосіб ознайомлення з інтерфейсом API.

### 2.2. Мета розробки

Метою є створення зрозумілої та розширюваної специфікації REST API, підготовка TypeScript-артефактів на основі OpenAPI та публікація централізованої технічної документації.

### 2.3. Основні завдання

1. Визначити основні сутності предметної області.
2. Спроєктувати операції CRUD для проєктів і завдань.
3. Описати API у форматі OpenAPI YAML.
4. Визначити структуру запитів, відповідей і кодів HTTP.
5. Згенерувати TypeScript-типи зі специфікації OpenAPI.
6. Створити документацію API засобами Zudoku.
7. Додати технічне завдання, інструкції з використання та інформацію про автора.
8. Розмістити вихідні матеріали в репозиторії GitHub.
9. Налаштувати автоматичне складання й публікацію документації на GitHub Pages.

## 3. Характеристика об'єкта автоматизації

Об'єктом автоматизації є процес опису та організації роботи з проєктами й завданнями.

Система передбачає дві основні сутності.

### 3.1. Сутність Project

Сутність `Project` описує окремий проєкт, у межах якого організовуються завдання.

Основні атрибути:

- `id` — унікальний ідентифікатор проєкту;
- `name` — назва проєкту;
- `description` — опис проєкту;
- `createdAt` — дата й час створення;
- `updatedAt` — дата й час останнього оновлення.

### 3.2. Сутність Task

Сутність `Task` описує окреме завдання, яке може бути пов'язане з певним проєктом.

Основні атрибути:

- `id` — унікальний ідентифікатор завдання;
- `projectId` — ідентифікатор пов'язаного проєкту;
- `title` — назва завдання;
- `description` — опис завдання;
- `status` — поточний стан завдання;
- `createdAt` — дата й час створення;
- `updatedAt` — дата й час останнього оновлення.

Наведені атрибути є проєктною моделлю. Остаточні назви полів, обов'язковість і допустимі значення мають відповідати схемам у файлі `api/openapi.yaml`.

### 3.3. Взаємозв'язок сутностей

Один проєкт може містити декілька завдань. Кожне завдання має бути пов'язане з проєктом за допомогою ідентифікатора `projectId`, якщо така модель передбачена специфікацією.

## 4. Функціональні вимоги

### 4.1. Управління проєктами

Система повинна передбачати такі операції:

- створення нового проєкту;
- отримання списку проєктів;
- отримання інформації про конкретний проєкт;
- редагування даних проєкту;
- видалення проєкту.

### 4.2. Управління завданнями

Система повинна передбачати такі операції:

- створення нового завдання;
- отримання списку завдань;
- отримання інформації про конкретне завдання;
- редагування даних завдання;
- видалення завдання;
- отримання завдань певного проєкту, якщо така операція передбачена API.

### 4.3. Валідація даних

API має перевіряти коректність вхідних даних відповідно до визначених схем. Необхідно передбачити обробку відсутніх обов'язкових полів, некоректних типів даних та ідентифікаторів ресурсів, які не існують.

### 4.4. Обробка помилок

Для помилкових запитів необхідно передбачити зрозумілі HTTP-коди та структуровані повідомлення про помилки. Формат відповіді має бути описаний у специфікації OpenAPI.

### 4.5. Документування API

Документація повинна містити опис доступних операцій, параметрів, схем даних, можливих відповідей та прикладів запитів. Інформація має відповідати актуальній специфікації OpenAPI.

## 5. Вимоги до зовнішніх інтерфейсів

### 5.1. Програмний інтерфейс

Взаємодія з API має здійснюватися за протоколом HTTP із використанням методів відповідно до призначення операцій:

- `GET` — отримання даних;
- `POST` — створення ресурсу;
- `PUT` або `PATCH` — оновлення ресурсу;
- `DELETE` — видалення ресурсу.

Конкретні маршрути та методи визначаються у файлі `api/openapi.yaml`.

### 5.2. Формат даних

Для обміну структурованими даними рекомендується формат JSON із відповідним заголовком `Content-Type: application/json`.

Вхідні та вихідні дані повинні відповідати схемам, визначеним у специфікації OpenAPI.

### 5.3. Інтерфейс документації

Документація має бути доступна через веббраузер і містити навігацію між такими розділами:

- Installation;
- Authorization;
- About;
- Технічне завдання;
- API Reference.

Сторінки мають бути доступними за посиланнями та читабельними на поширених розмірах екранів.

## 6. Вимоги до безпеки

1. Серверна реалізація повинна перевіряти всі вхідні дані.
2. Помилки не повинні розкривати паролі, секретні ключі або внутрішні деталі серверної реалізації.
3. Якщо API використовує авторизацію, її механізм, необхідні заголовки та вимоги до доступу повинні бути описані в OpenAPI.
4. Секретні ключі й токени не можна зберігати у відкритому вигляді у вихідному коді або публічному репозиторії.
5. Для опублікованої документації слід використовувати HTTPS, якщо це підтримується середовищем розміщення.

Наявність авторизації та конкретний механізм захисту визначаються реалізацією API. Документація не повинна стверджувати, що механізм працює, якщо його не реалізовано.

## 7. Нефункціональні вимоги

### 7.1. Надійність

Специфікація OpenAPI повинна бути синтаксично коректною. Збірка документації має завершуватися без помилок.

### 7.2. Супроводжуваність

Вихідні файли мають зберігатися в системі контролю версій. Зміни до специфікації, документації та конфігурації необхідно фіксувати в Git.

### 7.3. Сумісність

Проєкт документації повинен збиратися в середовищі Node.js, сумісному з установленими залежностями Zudoku.

### 7.4. Зручність використання

Документація повинна мати зрозумілу структуру, логічну навігацію, читабельні описи й приклади. Терміни та назви сутностей мають використовуватися послідовно.

### 7.5. Продуктивність

Статична документація повинна завантажуватися без необхідності запуску окремого серверного застосунку на стороні користувача. Фактичні показники часу завантаження за потреби визначаються під час тестування.

## 8. Вимоги до програмної документації та SDK

### 8.1. Специфікація OpenAPI

Основний файл специфікації:

`api/openapi.yaml`

Він має містити інформацію про версію OpenAPI, назву API, доступні маршрути, операції, параметри, схеми запитів і відповідей та можливі помилки.

### 8.2. TypeScript

Для генерації TypeScript-типів використовується інструмент `openapi-typescript`.

Основний згенерований файл:

`sdk/generated/schema.d.ts`

Він містить типи, сформовані на основі OpenAPI. Цей файл не є повноцінним HTTP-клієнтом SDK: він забезпечує типізацію даних, а для автоматизованого виконання запитів потрібна окрема клієнтська реалізація або генерація клієнта відповідним інструментом.

### 8.3. Документація Zudoku

Документація повинна формуватися на основі специфікації OpenAPI й додаткових текстових сторінок. Текстові матеріали мають пояснювати призначення API, порядок ознайомлення з ним і правила взаємодії.

### 8.4. Репозиторій

У системі контролю версій повинні зберігатися специфікація API, згенеровані матеріали SDK, вихідні файли документації, конфігурація Zudoku та файли автоматизованого розгортання.

## 9. Вимоги до тестування та приймання

Програмний продукт вважається таким, що відповідає технічному завданню, якщо виконано такі перевірки:

1. Файл OpenAPI існує та містить опис основних сутностей і операцій.
2. Специфікація проходить перевірку синтаксису та структури.
3. TypeScript-типи генеруються без помилок.
4. Проєкт Zudoku успішно встановлює залежності й виконує production-збірку.
5. У документації доступні розділи Installation, Authorization, About і Технічне завдання.
6. API Reference відображає операції зі специфікації OpenAPI.
7. Репозиторій містить актуальні вихідні файли.
8. GitHub Actions успішно виконує збірку й публікацію документації.
9. Опублікована сторінка відкривається за адресою GitHub Pages.

Якщо серверна реалізація API не входить до складу проєкту, перевірка фактичного виконання HTTP-операцій проводиться лише за наявності доступного сервера. У такому випадку перевіряються специфікація, документація та згенеровані типи.

1. Проєкт виконується в межах навчального завдання.
2. OpenAPI є основним джерелом інформації про структуру API.
3. Згенеровані типи залежать від актуальності специфікації.
